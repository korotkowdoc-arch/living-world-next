# Запуск в сети: Supabase + Cloudflare Pages + Worker

## 1. Новая база без удаления старой

В Supabase открой SQL Editor проекта, которым хочешь пользоваться (можно прежним). Выполни **по порядку** `supabase/schema.sql`, затем `supabase/migrations/001_story_controls.sql`, затем `supabase/migrations/002_memory_retrieval.sql`, затем `supabase/migrations/003_atomic_world_creation.sql`, затем `supabase/migrations/004_agency_and_memory.sql`. Второй файл добавляет журнал правок правил, проверку запрета на уважение, квитанции и атомарное «На это». Если базовая схема уже была установлена, выполни только недостающие миграции по порядку (001, затем 002, затем 003, затем 004). Новые таблицы начинаются на `nw_`; существующие `lw_*` не затрагиваются. Проверь выполнение без SQL-ошибок. Скрипт не читает старые миры.

В Project Settings → API возьми **Project URL** и **publishable/anon API key**. НИКОГДА не вставляй `service_role` в приложение или переписку. В Supabase Authentication убедись, что Email/Password поддерживается, а CORS/Allowed redirect настроены для своего нового домена.

## 2. Веб-приложение для iPhone

Все файлы уже подготовлены в `public/`. Никакая локальная компиляция не требуется.

**Cloudflare Pages через GitHub:** создай независимый проект `living-world-next`, подключи новый репозиторий `korotkowdoc-arch/living-world-next`, укажи `public` как output directory, **без build command**, production branch `main`. Это автоматическая публикация на каждый новый push.

**Или direct upload из ПК:** `npx wrangler pages deploy public --project-name living-world-next` после авторизации и создания Cloudflare Pages проекта. Это альтернативный способ, не обязательно совмещать его с Git-integrated Pages.

Открой новый HTTPS-адрес на iPhone. Публичный URL Supabase и publishable key уже включены в `public/lib/public-config.mjs` для этого проекта: на первом входе нужен только email/password. Использовать чужой проект можно через ручное изменение конфигурации. Ключ `service_role` никогда не публикуется. Создай тестовый мир, открой заново, проверь сохранение, затем новую сцену и новую ветку.

## 3. OAuth для ChatGPT + отдельный MCP Worker

**Подготовлены исходники** для resource metadata, OAuth consent screen и проверки токена конкретного OAuth-клиента. Обменом authorization code + PKCE и refresh занимается сам Supabase Auth. **Работающий онлайн-коннектор ещё не подтверждён.**

1. В Supabase Authentication → OAuth Server включи OAuth 2.1 server capabilities и укажи Authorization Path `/oauth/consent.html`. В Authentication → URL Configuration Site URL должен указывать на **новый Cloudflare Pages-домен**, на котором лежит этот файл.
2. Создай (или динамически зарегистрируй через ChatGPT, если разрешено) отдельный OAuth client. Его Redirect URI берётся **из настройки твоего ChatGPT-подключения**, не угадывай его. Для client-а нужна выдача authorization code + PKCE и refresh tokens. Проверь discovery metadata Supabase на поддерживаемые scope и `offline_access` либо аналог.
3. В `worker/wrangler.toml` замени `SUPABASE_URL`, `MCP_PUBLIC_URL` (`https://имя.workers.dev/mcp`) и `SUPABASE_OAUTH_CLIENT_ID` на реальные значения OAuth-клиента. Сохранить только публичный API key в Worker secret `npx wrangler secret put SUPABASE_ANON_KEY --config worker/wrangler.toml`. Не используй service_role.
4. Опубликуй Worker `npx wrangler deploy --config worker/wrangler.toml`. Проверь его `/health` и `/.well-known/oauth-protected-resource`. Состояние `oauth_metadata_ready=true` лишь показывает заполнение конфигурации, а не успех входа.
5. Добавь кастомное MCP-подключение из доступного твоему аккаунту интерфейса ChatGPT, укажи URL `/mcp`, разреши OAuth доступ в consent-экране. Проверяй команду `list_worlds`, затем реальный `save_scene` и чтение той же сцены на iPhone. Возможность настройки custom MCP зависит от доступа/плана аккаунта; через мобильное приложение создание такого подключения может быть недоступно — первичную настройку проводи в браузере на ПК.

Если ChatGPT использует Dynamic Client Registration, ID клиента может измениться; `SUPABASE_OAUTH_CLIENT_ID` в Worker должен соответствовать **фактически выданному** клиенту. Нельзя подменять его старым ID без проверки.

## 4. Windows-терминал: локальные проверки

Репозиторий уже существует: `korotkowdoc-arch/living-world-next`, ветка `main`. Для обновления **локальных** исходников и прогонки тестов из папки проекта:

```powershell
git pull --ff-only; npm test; npm run check
```

Если ты продолжаешь работать с тем же локальным репозиторием, это обновит его без перезаписи твоих незакоммиченных изменений; при конфликте команда остановится. Сам сайт после GitHub push публикуется независимо только при подключённом Cloudflare Pages.

## 5. Реальные проверки после развёртывания

- Создай мир на iPhone одним предложением, закрой Safari, открой снова — запись должна сохраниться.
- Добавь инструкцию о непримиримости Гарри/Малфоя; перезапусти сайт, проверь правило. Потом измени/отключи правило: версия должна обновиться, журнал сохраниться, прежние сцены не исчезнуть.
- Добавь две текстовые сцены с резервным импортом, сделай «На это» на первой, укажи короткую уникальную фразу и введи альтернативное продолжение; старые две сцены должны остаться доступными при переключении ветки.
- Попробуй авторизоваться другим Supabase-аккаунтом и убедись, что чужих миров/сцен нет.
- Одновременно сохрани два разных текста с одним и тем же expected_head: один должен получить CAS conflict. Повтор с тем же `request_id` не создаёт второго ID.
- Сверь на настоящих сценах, что непримиримость, психология, знания и ресурсы остались правильными. Компиляция и автотесты не доказывают литературной убедительности.

## 6. Границы подтверждённой работоспособности

На 2026-11-23 проверены только Node-тесты, mock OAuth и синтаксис. SQL `001_story_controls.sql` не испытан на реальном Postgres и должен быть проверен прежде, чем утверждать, что атомарное «На это» работает в облаке. Не запускай миграцию на старом `lw_*` проекте, если хочешь полностью независимые базы: новый `nw_*` namespace в прежнем Supabase безопаснее с точки зрения таблиц, но использует тот же Auth-проект.

## 7. Проверки v0.3

После миграции 002 в интерфейсе открой мир → **Поиск**. Вбей фразу из ранней сцены, убедись, что результат содержит текст и может открыть полный оригинал. Во вкладке **Персонажи** найди героя по имени: показываются только структурированные события с источниками, не придуманные черты характера. В «Режиссёр» → **Резервная копия мира** экспортируй JSON: в него включаются все ветки, не только действующая. После экспорта загрузи этот же файл в поле проверки, проверь совпадение SHA-256. **Не удаляй онлайн-мир**: обратный импорт пока не реализован.

На iPhone Safari через «Поделиться → На экран Домой» можно добавить PWA. Офлайн доступна только оболочка; личная история продолжает загружаться из Supabase, не сохраняется в кэше service worker. Никогда не помещай секреты в публичный каталог `public/`.

## 8. Атомарный быстрый старт v0.3.1

Миграция 003 добавляет `nw_create_world_v2`: создание мира и закрепление явных запретов из исходной фразы проходят в **одной** SQL-транзакции. Без неё новая версия сайта не сможет создать новый мир. В обычной ситуации никакой ручной разметки NPC всё равно не нужно. Реальная облачная транзакция требует теста на Supabase после миграции: ввести один мир с прямым запретом на примирение, убедиться, что появилось ровно одно правило и один мир, что при повторе не осталось дубликата.

## 9. Пакет 0.4 — долгосрочная память и подтверждаемые намерения NPC

Миграция `004_agency_and_memory.sql` **обязательна** для этой версии MCP и интерфейса; без неё `get_world_context`, `get_npc_agency` и «загрузить планы из всей истории» вернут ошибку неизвестной RPC. Применять после миграции 003. Старые таблицы `lw_*` не затрагиваются.

- Сохранение сцены с тем же `request_id` повторно допускается только при дословном совпадении текста, событий, ожидаемой родительской сцены, времени и версии правил. Это защищает от дублей после сетевого сбоя. Если изменил текст, генерируется новый ID.
- `nw_active_memory_page` читает события действующих предков по 200 записей и привязан к конкретному `head_scene_id`; при смене вершины нужно перезапросить контекст. Проза остаётся в `get_story_scene`/поиске, а в расчёте памяти участвуют **только сохранённые структурированные события**. Пустой набор событий не доказывает, что ничего не случилось.
- События `plan` фиксируют цель и жизненный цикл (`start`, `advance`, `pause`, `resume`, `complete`, `abandon`). Для `complete` необходимо фактическое `world` или `offscreen` событие с ID в той же сцене. Сохранение не запускает героев в фоне — действия придумывает и подтверждает рассказчик в ChatGPT во время игры.
- `get_story_scene` дополнительно вызывает `nw_scene_in_active_branch` и маркирует альтернативные сцены, чтобы они не попадали в текущие воспоминания.

**Проверка:** после установки миграции создай тестовый мир и несколько сцен (включая намерение NPC и его подтверждённое событие); проверь вкладку «Персонажи», `get_npc_agency`, совпадающий повтор `request_id`, отказ на изменённое содержимое с прежним ID, пометку альтернативной сцены. Не утверждай, что это сделано, без фактического онлайн-теста.

## v0.5: MCP уже внутри Cloudflare Pages

Код `functions/[[path]].js` и `public/_routes.json` разворачивается автоматически при push в уже подключённый проект Pages. Старую секцию об отдельном `worker/wrangler.toml` следует считать альтернативным, **необязательным** способом развёртывания. Основной URL MCP: `https://living-world-next.pages.dev/mcp`. Отдельный workers.dev не нужен.

Проверить `https://living-world-next.pages.dev/health` и `https://living-world-next.pages.dev/.well-known/oauth-protected-resource`. Затем в Supabase (Authentication > OAuth Server) включить сервер и настроить Authorization Path, отдельного клиента OAuth 2.1 для NEXT, и в Cloudflare Pages Production Variables задать `SUPABASE_OAUTH_CLIENT_ID`. OAuth Redirect URL строго из ChatGPT. Старый LIVING WORLD OAuth клиент не изменять.

Проверить MCP initialize, tools/list, unauthenticated tools/call → HTTP 401. Прохождение этих тестов само по себе не доказывает пользовательский OAuth E2E.
